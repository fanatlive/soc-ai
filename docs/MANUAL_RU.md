# SOC AI Triage — полное руководство

> Краткое описание проекта — в [README](../README.md). Команды ниже выполняются из корня репозитория.

Рабочий локальный MVP для первичного разбора SOC-алертов: FastAPI, SQLite, шесть детерминированных правил, OpenAI-совместимый LLM API и адаптивная панель на русском языке. Аналитик принимает окончательное решение. Приложение не исполняет команды и не изменяет инфраструктуру.

## Быстрый запуск

Нужен Python **3.11+**. Все команды выполняются из папки `soc-ai-triage`. Для работы без LLM API-ключ не нужен. Node.js не требуется: скомпилированный Tailwind CSS включен в проект, CDN и внешних шрифтов нет.

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade "pip>=26.2.0"
python -m pip install -r requirements.txt
cp .env.example .env
python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

**Windows PowerShell** — команды не требуют изменения ExecutionPolicy:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade "pip>=26.2.0"
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Откройте **http://127.0.0.1:8000**. Машиночитаемая спецификация API: **http://127.0.0.1:8000/openapi.json**. Сервер останавливается `Ctrl+C`. Для разработки можно добавить `--reload`.

При первом старте автоматически применяются версионированные миграции и создаются пять синтетических алертов. Повторный запуск не дублирует демо. SQLite-файл `soc_triage.db` хранится в текущей рабочей папке; запускайте сервер из одной и той же папки для сохранения истории.

## Демонстрация за несколько минут

1. На Dashboard откройте «Подбор пароля · admin».
2. Посмотрите исходный JSON и доказательства R001/R002. Нажмите «Анализировать с ИИ».
3. Без настроенного провайдера появятся `Critical`, режим «Только правила» и предупреждение. Это реальный локальный анализ, а не имитация LLM.
4. Введите комментарий и сохраните решение. В History появятся анализ и решение аналитика.
5. Повторите анализ: появится отдельная версия, старый результат и решения сохранятся. Новый анализ снова требует решения.
6. Добавьте свой лог, затем перезапустите сервер и проверьте сохраненные данные.

Ожидаемые результаты **только для поставленных синтетических примеров** в `rules_only`:

| Событие | Признаки | Ориентир |
| --- | --- | --- |
| 50 неудачных входов в admin и успешный вход | R001, R002 | Critical |
| PowerShell с загрузкой, IEX, Bypass и Hidden | R003, R005 | High |
| 30 различных портов за 45 секунд с внутреннего IP | R004, R005 | Medium |
| Три неудачных входа | Нет порогового индикатора | Low |
| Геоаномалия и аттестация корпоративного VPN | R006 | Low, возможно легитимно |

Эти уровни не являются универсальными правилами классификации. До первого анализа критичность показывается как «Не оценено»; статистика высокого риска вычисляется по последним сохраненным анализам, включая события с решением аналитика.

### Пустая база и загрузка демо

Установите `AUTO_SEED_DEMO=false` перед запуском, чтобы начать с пустой базы. В пустой очереди доступна кнопка «Загрузить 5 демо-событий». Также можно вызвать `POST /api/demo/seed` без тела. Операция идемпотентна и не перезаписывает существующие события, анализы или решения. При заданном API_TOKEN нужен Bearer-токен.

### Проверка поступления логов: 25 событий в секунду

События в очереди создаются через **POST `/api/alerts`**. Запрос **GET `/api/health`** проверяет доступность сервера и не добавляет SOC-логи. MVP принимает логи через API и форму; сетевой трафик других приложений автоматически не перехватывается.

При запущенном сервере выполните из папки проекта, используя Python установленного виртуального окружения:

```bash
python -m tools.generate_events --rate 25 --seconds 10 --analyze
```

Сначала генератор за 10 секунд отправит 250 синтетических логов через настоящий API со скоростью 25 запросов/с. Затем отдельным этапом запустит анализ сохраненных событий с той же скоростью. Без LLM используется `rules_only`; при настроенном LLM флаг `--analyze` обращается к выбранному провайдеру. Уберите этот флаг для проверки только приема логов.

Логи содержат `synthetic=true`, идентификатор `test_run` и пять типов демонстрационных сценариев. В Alerts они подписаны «Тест 25/с». Отчет показывает HTTP-статусы, количество запросов в каждой секунде и количество записей, повторно прочитанных через API. API_TOKEN берется из `.env`. Генератор поддерживает только локальный HTTP origin.

Очередь, статистика и History обновляются каждые **3 секунды** в видимой вкладке. При открытой форме или деталях фоновое обновление приостанавливается; черновик, фильтры и количество загруженных страниц сохраняются.

Проверено на локальном MVP: 250 событий и 250 анализов при 25 запросах/с на каждом этапе, все ответы 200. Еще 25 событий проверили автообновление в Chrome: счетчик изменился с 256 до 281 без ручного обновления страницы. Всего добавлено и проанализировано 275 синтетических событий.

## Настройка `.env`

В репозиторий включен только `.env.example`. `.env`, файлы БД, `.venv` и `node_modules` исключены через `.gitignore`.

| Переменная | Назначение / значение по умолчанию |
| --- | --- |
| `LLM_API_KEY` | Ключ провайдера; пусто — правила без LLM |
| `LLM_BASE_URL` | Базовый URL совместимого API, по умолчанию `https://api.openai.com/v1` |
| `LLM_MODEL` | Действительный идентификатор модели вашего провайдера; по умолчанию пусто |
| `LLM_TIMEOUT_SECONDS` | Общий таймаут и таймаут HTTP-операций, 25 секунд; допустимо 1–120 |
| `LLM_MAX_CONCURRENCY` | Максимум одновременных HTTP-вызовов LLM в одном процессе, 4; допустимо 1–16 |
| `LLM_QUEUE_TIMEOUT_SECONDS` | Ожидание свободного слота LLM, 2 секунды; допустимо 0.1–10 |
| `DATABASE_URL` | `sqlite:///./soc_triage.db`; другие СУБД в MVP не поддерживаются |
| `AUTO_SEED_DEMO` | `true` — загрузка пяти демо-событий при старте |
| `TRUSTED_NETWORKS` | CIDR через запятую, по умолчанию `192.168.0.0/16` |
| `ALLOWED_ORIGINS` | Доверенные origin, по умолчанию localhost/127.0.0.1 на порту 8000 |
| `ALLOWED_HOSTS` | Разрешенные Host, по умолчанию localhost, 127.0.0.1, [::1] |
| `API_TOKEN` | Секрет доступа к чтению и изменению событий, от 24 символов; пусто — API только с loopback |

Для LLM заполните ключ, базовый URL и модель, затем перезапустите сервер. Сервис отправляет настоящий `POST {LLM_BASE_URL}/chat/completions` через `httpx`, с Bearer-аутентификацией и `response_format=json_object`. Провайдер должен поддерживать этот контракт. При внешнем URL обязателен HTTPS; HTTP разрешен только для локального провайдера. Перенаправления HTTP отключены.

При недоступности, HTTP-ошибке, таймауте или занятых слотах провайдера автоматически сохраняется `rules_only`. Причины различаются безопасными кодами: `credentials_rejected`, `permission_denied`, `configuration_error`, `quota_or_rate_limit`, `provider_busy`, `timeout`, `network_error`, `provider_error`. После 429 действует пауза по Retry-After (1–60 секунд, по умолчанию 10); автоматических повторов нет. Если успешный HTTP-ответ содержит невалидный JSON, неподтвержденную цитату или действие вне Playbook, API возвращает **503** и заголовки `X-Analysis-Error` / `X-Request-ID`, алерт получает `error`, результат анализа не сохраняется. Сама попытка и безопасная причина сохраняются отдельно. Для чистого резервного режима оставьте ключ или модель пустыми и перезапустите сервер.

Настройка ключа сама по себе не подтверждает доступность провайдера. Состояние LLM: `not_configured`, `not_checked`, `ready` после успешной проверки ответа и `degraded` после ошибки. Перезапуск сбрасывает оперативную диагностику; история попыток остается в БД.

`hybrid` означает, что LLM получил результаты правил; `llm` — LLM без сработавших правил; `rules_only` — LLM не использовался. UI честно подписывает источник результата.

## Формат собственных логов

Любой непустой текст длиной до **2000 символов** можно сохранить. Для детерминированного разбора входов, портов и VPN используйте JSON-объект, JSON-массив, `{"events":[...]}`, JSON Lines или строки `key=value`. Произвольный текст поддерживается для PowerShell и LLM, но не превращается в выдуманные структурированные события.

Пример агрегированной серии входов с явным временным окном:

```json
{
  "events": [
    {"type":"failed_login","user":"demo","count":10,"window_seconds":60,"at":"2026-11-06T04:00:00Z"},
    {"type":"successful_login","user":"demo","at":"2026-11-06T04:00:10Z"}
  ]
}
```

Пример строки:

```text
type=failed_login user=demo count=10 window_seconds=60 at=2026-11-06T04:00:00Z
```

Поддерживаемые поля:

- `type` / `event_type` / `event`; `at` / `timestamp` с часовым поясом, не раньше 1970 года.
- `failed_login`, `login_failed`, `auth_failure`: `user`, `count` (по умолчанию 1), `window_seconds` (по умолчанию 0). `at` — конец агрегированного окна.
- `successful_login`, `login_success`, `auth_success`: `user`, `at`.
- `process_start`: `command` или `command_line` с PowerShell-командой.
- `port_scan`, `connection`, `network_connection`: `ports` (массив) либо `dest_port`, `window_seconds`, `at`.
- `corporate_vpn`: объект `{"verified":true,"verification_source":"synthetic-vpn-gateway"}`. Строка `"true"` не считается подтверждением.
- `source_ip` внутри записи необязателен: при отсутствии используется IP алерта. При наличии учитывается IP записи.

R001: не менее 10 неудачных входов в течение 300 секунд, сгруппированных по IP и пользователю. R002: не менее 10 неудачных входов перед успешным за те же 300 секунд с совпадением IP и **известного** пользователя. R003: encoded command, загрузка, динамическое выполнение, bypass или hidden у PowerShell. R004: не менее 20 различных портов за **60 секунд**; повторения одного порта не повышают счетчик. R005/R006 — только контекст. Все доказательства содержат ссылки на JSON-записи или номера строк.

Это анализ записей **внутри одного алерта**, без сложной межсобытийной корреляции. Агрегаты предполагаются неперекрывающимися. Аттестация VPN из пользовательского лога требует проверки по доверенному шлюзу; приложение самостоятельно ее не подтверждает.

В резервном режиме сочетание R001/R002 дает High, а имя admin/root/administrator повышает демонстрационный приоритет до Critical. Для R003 два или более параметров дают High, один — Medium. Это прозрачные эвристики, требующие проверки человеком.

## API и история

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/health` | Публично: status и необходимость токена; локально/с токеном: конфигурация и состояние провайдера без секретов |
| GET | `/api/stats` | Счетчики, число событий за 60 секунд и время последнего поступления |
| GET | `/api/alerts` | Совместимый список; `q`, `status`, `limit` (1–500), `offset` |
| GET | `/api/alerts/page` | Поиск по всей БД: `q`, `status`, `limit`, `cursor`; ответ `{items,total,next_cursor}` |
| POST | `/api/alerts` | Создание: source_ip, event_type, raw_data, опционально timestamp |
| GET | `/api/alerts/{id}` | Лог, текущие правила, последний анализ, решения и попытки |
| POST | `/api/alerts/{id}/analyze` | Новый сохраненный анализ; тело не требуется |
| GET | `/api/alerts/{id}/analyses` | Все версии со снимком правил, новые первыми |
| GET | `/api/alerts/{id}/attempts` | Успешные, неудачные и прерванные попытки с безопасными кодами ошибок |
| POST | `/api/alerts/{id}/decision` | analysis_id, decision, comment |
| GET | `/api/history` | Общая история с решениями по каждой версии; limit (1–200), offset |
| POST | `/api/demo/seed` | Идемпотентная загрузка демо |

Поиск `q` (до 120 символов) выполняется по типу события, IP и UUID без учета регистра, включая кириллицу. `%` и `_` считаются обычными символами. Фильтры применяются до пагинации. Курсор использует `(created_at, id)`; новые поступления не сдвигают уже загружаемую страницу. `total` — текущее полное количество совпадений.

Все успешные запросы возвращают 200. Ошибки: 409 — уже идет анализ или решение по устаревшей версии; 422 — ошибка данных; 503 — невалидный ответ LLM либо недоступная БД. Дополнительно используются 401/403 для доступа, 404 для отсутствующего алерта, 413 для HTTP-тела больше 16 КиБ. Ошибки валидации не возвращают исходные данные.

Пример тела решения:

```json
{"analysis_id":"UUID последнего анализа","decision":"confirmed","comment":"Проверено аналитиком"}
```

`decision` — `confirmed` или `false_positive`. Решение ссылается на конкретную версию. По старой версии новое решение запрещено; предыдущие решения остаются в истории. Повторный анализ не меняет старые записи и сбрасывает текущий статус на `analyzed`.

Время хранится в UTC и возвращается с часовым поясом; интерфейс показывает локальное время устройства. Состояния: `new`, `processing`, `analyzed`, `confirmed`, `false_positive`, `error`.

У анализа есть атомарная блокировка в БД с уникальным токеном и сроком 180 секунд. HTTP-вызов ограничен общим таймаутом максимум 120 секунд. При ошибке блокировка освобождается; после аварийного завершения просроченная блокировка восстанавливается при следующем запросе или запуске. Короткие SQLite-транзакции анализа выполняются в пуле потоков, каждая со своей Session. Обычный опрос не пишет в БД, если просроченных блокировок нет. Рекомендуемый режим MVP — один процесс Uvicorn.

## Обновление БД и диагностика

Миграции выполняются автоматически при запуске, версия хранится в `schema_migrations`. Версия 1 учитывает существующие таблицы v2.0, версия 2 добавляет `analysis_attempts`, версия 3 повторно маскирует распознаваемые секреты в старых логах, анализах и комментариях. UUID, даты, результаты и решения сохраняются; более новая неизвестная версия БД отклоняется. Обратные миграции не предусмотрены.

Перед обновлением сохраните резервную копию SQLite через backup API либо скопируйте файл при полностью остановленном сервере. Копия старых данных может содержать еще не замаскированные секреты: храните ее локально с ограниченными правами. В текущей рабочей папке перед обновлением создана закрытая копия в `backups/`; она исключена из Git и архива проекта.

Каждый принятый запуск получает отдельную попытку: `processing` → `succeeded`, `failed` или `abandoned`. Успешный резервный анализ может содержать `provider_error_code`; это завершенный локальный анализ с ошибкой внешнего провайдера. Невалидный ответ сохраняет только попытку с `error_code`. Старым анализам попытки задним числом не придумываются. В деталях архивной версии отображается сохраненный снимок `rule_findings`, а не пересчитанные текущие правила.

Практические результаты исправлений и границы проверки: [технический отчет](TECHNICAL_IMPROVEMENTS_RU.md). Требования к будущим слайдам и демонстрации: [ТЗ для презентации](PRESENTATION_BRIEF_RU.md).

## Безопасность и смысл оценок

- Ключи берутся из `.env` / окружения и не передаются в API-ответах. В JSON/JSONL чувствительные ключи распознаются без учета регистра и разделителей; значение маскируется целиком, включая числа, массивы и объекты. Поддерживаются X-API-Key и X-Goog-API-Key. Для текста используется дополнительное маскирование. Распознаваемые пароли, токены, Bearer-ключи и приватные ключи маскируются **до сохранения**, повторно перед LLM и при сериализации. Сырые секреты после маскирования не восстанавливаются. Регулярные выражения не гарантируют обнаружение секрета произвольного формата; используйте синтетические данные.
- LLM получает системные ограничения, Playbook и отдельное поле недоверенного лога. Ответ проверяется Pydantic v2. Провайдер возвращает `evidence: [{source, quote}]`: каждая точная цитата должна содержаться в указанном источнике. Публичное описание доказательства формирует сервер. Провайдер выбирает только `recommended_action_ids` из `playbook.allowed_actions`; текст рекомендаций задается сервером. Неизвестные IP, распознаваемые заявления о подтверждении человеком и очевидные разрушительные инструкции в свободном тексте отклоняются. Это ограниченная проверка: семантическая правильность резюме и релевантность цитат требуют проверки аналитиком.
- Модель не получает инструментов, доступа к shell или инфраструктуре. Рекомендации остаются текстом. HTML из логов и ответов экранируется; CSP запрещает внешние и встроенные скрипты.
- SQLite используется через SQLAlchemy, включены внешние ключи. История анализов и решений дополняется, а не перезаписывается.
- `false_positive_score` в этом MVP всегда **null**: данных для достоверной оценки нет. `confidence` у LLM — только самооценка модели, а не измеренная точность или вероятность атаки. В `rules_only` confidence тоже null.
- Никакой результат AI не помечается решением человека. Статусы confirmed/false_positive задаются только через явное действие аналитика.

### При внешнем размещении

По умолчанию сервер слушает только `127.0.0.1`. Без API_TOKEN чтение и изменение событий извне запрещены. Если нужен внешний доступ, задайте случайный API_TOKEN длиной не менее 24 символов и точные ALLOWED_HOSTS/ALLOWED_ORIGINS. В UI токен вводится через значок ключа / профиль; хранится только в памяти вкладки. Запросы используют `Authorization: Bearer ...`.

API_TOKEN защищает **чтение и изменение бизнес-данных**. Без токена публичен только минимальный `/api/health`; HTML, статические ресурсы и OpenAPI не содержат данных событий. После удаления токена UI очищает загруженные данные. Для внешнего размещения используйте TLS, ограничьте доступ к сети и настройте доверие к proxy-заголовкам; не считайте IP reverse proxy подтверждением локального клиента. CORS не заменяет аутентификацию. Многопользовательская авторизация и аудит личности в MVP не реализованы.
